## The finding

`decisions.md` Section 12's third frozen support condition reads:

> every **adjusted** baseline covariate has absolute standardized mean
> difference (SMD) < 0.10

`src/causal/overlap.py::_smd` takes two value sequences and no weights, and
those sequences are built from raw `PatientRecord.timeline.static_covariates`
reads. It therefore measures **raw, unweighted** covariate balance. The wording
"adjusted" is not implemented.

This is not a cosmetic gap. `decisions.md` Section 9's observationalization
mechanism *deliberately* selects on `baseline_cd4`, `karnofsky_score`, `age`,
`symptomatic_status`, `prior_opportunistic_infection`, and `prior_art`. Raw
imbalance on exactly those covariates is the benchmark's designed confounding
signal — the thing the pipeline is built to induce and then adjust away. The
current condition therefore fails whenever the mechanism works.

### The n discrepancy (resolved)

Task 7.2's task text states dev-retained n=378 with arms {1: 205, 0: 173} and
ESS {1: 187.1, 0: 148.6}. The committed `scripts/run_causal_analysis.py` seed
derivation yields n=383, arms {1: 201, 0: 182}, ESS {1: 187.23, 0: 161.00}.

The cause is a **seed-derivation-path difference**, confirmed by direct
reproduction: passing `20240101` *un-derived* to both
`run_observationalization_pipeline` and `LogisticPropensityModel` reproduces
every task-text number exactly — n=378, arms 205/173, ESS 187.0905/148.5527,
`extreme_weight_count=1`, and all six raw SMDs to four decimals.
`scripts/run_causal_analysis.py` instead derives them
(`derive_seed(master_seed, "causal_analysis_pipeline")` at line 311,
`derive_seed(master_seed, "propensity")` at line 327). Neither number is
adopted here. The committed script is the canonical path, so the task text's
numbers should be treated as measured off a non-canonical seed path and the
task text corrected — but that is a spec-text fix, not a decisions.md
amendment, and it is not made here.

Note that this also affects task 7.3: the "exactly 1 patient of 378 outside the
primary band" it is scoped to investigate exists only on the un-derived path.
On the canonical path `extreme_weight_count = 0` and
`no_unresolved_positivity_warning` **passes**.

## Correction: Section 11.3 does not forbid adjusting for baseline CD8

The evidence section above (table B commentary) states that `baseline_cd8`
"cannot be added" to the propensity model because Section 11.3 /
`data.leakage_audit.assert_no_self_adjustment` forbid adjusting for it. That
is a misreading. Section 11.3's double-use safeguard scopes the exclusion to
one regression only:

> in the negative-control-outcome regression only, baseline CD8 is excluded
> from the right-hand-side adjustment set (all other baseline covariates are
> retained);
>
> in every other model (propensity model, outcome regression, GRU
> state-prediction head), baseline CD8 continues to serve its normal role as
> an adjustment covariate or prediction target and is not otherwise
> restricted;

and adds that the rule "must not be read as removing CD8 from the adjustment
set elsewhere". `assert_no_self_adjustment` is called only inside
`causal.negative_controls.run_negative_control_outcome`, on that regression's
covariate list. Nothing in `decisions.md` keeps `baseline_cd8` out of the
propensity model; Section 13 puts it in.

The real reason `baseline_cd8` was unmoved by weighting is that
`causal.propensity.COVARIATE_FIELDS` does not conform to Section 13. Section 13
freezes a 13-covariate adjustment set (age; weight; sex; race/ethnicity;
hemophilia; homosexual activity; intravenous drug-use history; Karnofsky
score; prior opportunistic infection; symptomatic status; baseline CD4;
baseline CD8; prior antiretroviral exposure and duration, mirrored as
`adjustment_set` in `configs/target_trials/main.yaml`). `COVARIATE_FIELDS`
carries only six: `baseline_cd4`, `karnofsky_score`, `age`,
`symptomatic_status`, `prior_opportunistic_infection`, and `prior_art` (a
binary indicator, not exposure *and duration*). Those six are Section 9's
observationalization inputs, not Section 13's adjustment set.

Observed while checking this (not re-measured): the current
negative-control-outcome check is an outcome regression,
`baseline_cd8 ~ treatment_arm + (spec.adjustment_set minus baseline_cd8)`
(`negative_controls._fit_cd8_regression_smd`, called from
`scripts/run_causal_analysis.py` with `spec.adjustment_set`). It does not read
`COVARIATE_FIELDS` or any propensity score today, so extending the propensity
model does not by itself change that check's inputs. Item 3 of the decision
below is written so that it stays true if the check is ever computed with a
propensity-based (weighted) form.

### Expected consequences (not yet measured)

These are expectations, not results. Tasks 7.5 and 7.6 measure them.

- `baseline_cd8`'s weighted SMD is expected to fall below 0.10 once it is in
  the propensity model. If it still fails after adjustment, that is a genuine
  cohort finding, the third condition fails, and the gate stays blocked. The
  threshold is not revisited.
- Per-arm ESS is expected to stay above the 100 floor. The smallest arm today
  is arm 0 at 161.00 on the canonical path, but a 13-covariate model can
  produce more extreme propensities, so this is not guaranteed. Note that
  `OverlapDiagnostics` computes ESS from unstabilized, unclipped weights
  (unchanged by this amendment); stabilization does not affect per-arm ESS,
  but the weighted-SMD basis uses clipped weights.
- Every conventional estimate that reads `COVARIATE_FIELDS` changes: the
  propensity scores, every IPW / IPCW-AIPW estimate, `adjusted_cox`, and
  `models.non_neural_baseline.CoxBaseline` (whose `COEFFICIENT_NAMES` is
  `("treatment_arm", *COVARIATE_FIELDS)`). This is acceptable only because the
  Test_Split and the sealed reference are still sealed. No estimate has been
  evaluated on test data, so no result is being re-chosen after seeing it.
- `extreme_weight_count` (0 on the canonical path today) may change, since it
  counts patients outside the primary band under the new propensity scores.

### Name mismatch between Section 13 and the stored concept ids

The adjustment-set names in `configs/target_trials/main.yaml` do not all
match the `static_covariates` keys the loader writes. This is part of why
item (4) is needed. Checked in source, not re-measured on the real cohort:

| Section 13 / `adjustment_set` name | loader concept id (`actg175_adapter.py`) | after `concept_unit_mapping.yaml` |
|---|---|---|
| `weight` | `weight_kg` | `weight` |
| `intravenous_drug_use_history` | `iv_drug_use_history` | not remapped |
| `prior_antiretroviral_exposure_and_duration` | `prior_art_exposure_days` | `prior_antiretroviral_exposure_duration` |
| `sex` | `sex` (`"M"`/`"F"` string) | not remapped |
| `race_ethnicity` | `race_ethnicity` (free string) | not remapped |

Because of this, a lookup by the Section 13 name can return `None` even when
the value is present under another key, and `_raw_numeric_covariate` cannot
parse the string-valued `sex` and `race_ethnicity` at all. Task 7.5 must
define one explicit Section-13-name → concept-id(s) → encoding mapping,
shared by the propensity model and the balance report, rather than relying
on name equality.

### Downstream width change in the neural stack

`src/models/dataset.py` builds `TensorBatch.baseline` with columns in
`causal.propensity.COVARIATE_FIELDS` order, using that module's
`_fit_standardization` / `_feature_vector`, and reports
`DatasetDimensions.baseline_covariate_width = len(COVARIATE_FIELDS)`
(confirmed in `PatientDatasetBuilder.dimensions`). Extending
`COVARIATE_FIELDS` therefore changes `baseline_covariate_width` and the shape
of `TensorBatch.baseline` from `(N, 6)` to `(N, k)`, where `k` is the number of
encoded columns 7.5 specifies (13 or more if any categorical is one-hot
encoded).

What this touches in the neural models:

- `TorchInterventionAwareModel` carries `batch.baseline` through unread by any
  encoder, but validates its width against
  `dimensions.baseline_covariate_width`. The encoder widths (4/3/2) and
  hidden width 16 frozen in Section 25 do not change.
- `TorchSequenceGRU` initializes its hidden state from
  `models.sequence_baseline.BASELINE_STATE_INIT_FIELDS`, its own list, not
  `COVARIATE_FIELDS`, so its layer widths do not change.
- Tests that derive the width from `len(COVARIATE_FIELDS)`
  (`tests/neural/test_dataset.py`, `tests/neural/test_dataset_builder.py`)
  should follow automatically. Any neural test or fixture that pins the
  literal width 6, or builds a `DatasetDimensions` / baseline tensor by hand,
  needs updating in 7.5.
- The docstring in `src/models/torch_intervention_aware.py` states that
  `baseline_cd8` is not in `COVARIATE_FIELDS`. That becomes false and should
  be corrected in 7.5.
- Already-written checkpoints and the task 10 results were produced at width
  6. They are development-stage artifacts, and the next checkpoint run
  regenerates them.

The diagnostic tests encode the superseded reading and will need updating in
7.6. `tests/diagnostics/test_overlap_diagnosis.py` asserts that any residual
weighted offender is absent from `COVARIATE_FIELDS`, and
`tests/diagnostics/test_positivity_and_negative_control.py` carries a verdict
string saying Section 11.3 forbids adjusting for `baseline_cd8`.
